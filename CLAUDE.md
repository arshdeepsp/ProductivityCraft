# CLAUDE.md — ProductivityCraft

Pixel-art gamified habit/productivity app. Web PWA (GitHub Pages) + Android app (Capacitor). All data local; no backend.

## Working with Arsh
- Keep answers short; lead with the answer.
- Pastable commands contain no comments; explain in prose outside the code block.
- Run `npm test` before calling anything done. Add a test for every behaviour change or bug fix.
- He tests on a real Android phone; native code can only be verified there.

## Commands
```
npm install
npx playwright install chromium
npm run build
npm test
npm run serve
npm run android:apk
```
- `build` → `dist/` (single `index.html` + assets + `sw.js` with versioned cache).
- `test` → build + Playwright (headless Chromium, fake clock, seeded localStorage), served over http by `tests/serve.mjs` on :4173 (file:// lost localStorage across reloads and made reload tests flaky). ~110 tests, ~2 min.
- `android:apk` → build, `npx cap sync android`, `node scripts/add-native.cjs`, `./gradlew assembleDebug`. Never run `assembleDebug` alone after source changes.
- First Android setup: `npx cap add android`, `node scripts/add-permissions.cjs`, `npx @capacitor/assets generate --android`, then `npm run android:apk`.
- Push to `main` → GitHub Actions runs tests, deploys `dist/` to Pages only if green.

## Layout
```
src/index.html         markup with /*@inject:css|ach|js*/ points
src/styles/NN-*.css    concatenated in filename order
src/js/NN-*.js         concatenated in filename order inside ONE closure
src/assets/achievements.json
public/                static files copied to dist (fonts, icons, vendor, manifest, sw.template.js)
native/android/        FocusNotifier/FocusNotifyPlugin/FocusNotifyReceiver (Java), layouts, icon, pc_chime.wav
scripts/               add-native.cjs, add-permissions.cjs (.cjs because package.json is "type": "module")
tests/*.spec.mjs       Playwright specs; helpers.mjs has openApp() and dayRange()
build.mjs              the whole build
```
- All JS shares one scope. Function declarations are hoisted, but top-level `var`s and immediate code run in file order. A `var` used during startup must be defined in an earlier file (this has bitten us).
- File names reflect history, not features. Use grep. Examples: starter packs live in `07-generic-drag-to-reorder.js`; weekly totals in `26-momentum-bank-rolling-targets-sessions.js`; notifications in `35-quest-subject-links-finish-lines-cap.js`.
- Two dist-only artifacts exist outside the repo (old claude.ai artifact, old `productivitycraft-android` folder). Both are retired; this repo is the only source.

## State and data
- Global `S` = `{days, refl, cfg, timer, sprint, ...}`; persisted to `localStorage["pc-cache-v1"]` via `cache()`.
- `cfg()` returns settings; change settings with `saveCfg(clone)`. Edit today via `entry()` then `commit()`.
- No store/subscriptions: after a change, call `render()` (and `qSig=""` if the quest list structure changed). Forgetting this is a common bug.
- Each day entry stores a snapshot of its quest defs in `e.q` (`slim()` decides which fields are copied — add new quest fields to that list).
- **Past days are frozen** (`lockPast`, 26, run at the start of `render` and `compute`): every passed day without a snapshot gets `e.q = activeDefs(k)` as it stood when the day ended, plus `e.ck` = ids of totals whose halfway checkpoint fell on it. So later edits, pauses and deletions never rewrite history. `dayDefMap(d)` = quests on day d (snapshot for past days, live for today on). `hasEntry` ignores `ck`; `firstSeen` skips auto snapshots. A snapshot made for a day the app wasn't opened applies scheduled changes already due (`lockDefs` → `pendingApplied`, 36). Repeats that fell on a passed day are copied onto it (`lockReps`: one-offs with `src` + `schSkip`; `cfg.repFrozen` marks the one-time catch-up), so stopping a repeat never changes past plans. `lockPast` resets when `START_KEY` changes or after an import (`lockReset`) and is skipped while `cacheBlock`. SCHEMA 12 marks this. Import takes a backup's `q`/`ck` for days with nothing logged locally. SCHEMA 14: data upgraded from older versions gets `cfg.ckFrom` (upgrade day) — halfway checks only apply to periods starting on/after it, and older `ck` are cleared.
- Unreadable saved data, or data from a newer schema, is copied to `pc-cache-rescue` and `cacheBlock` stops `cache()` from writing over it (a modal explains) until a backup is imported.
- `SCHEMA` and `migrate()` in `00-core.js`. Changing stored shape: bump SCHEMA, add a migrate step, add a test in `tests/data.spec.mjs`. Backups from a newer schema are refused.
- UI-only prefs live in separate localStorage keys (`pc-focusview`, `pc-doneopen`, `pc-adv`, `pc-todoreview`, ...).

## Core rules (keep tests green when touching these)
- **Day cleared**: every required quest met and no limit broken. Required (`reqOf`) = not optional, not weekly-X-times, not to-do, not a period total (`q.roll`). Nothing required → rest day.
- **Period totals are judged twice** (`periodCheck` in `compute`). Work days (`workOn`): on that day's list, scheduled, not off, not on vacation (paused days aren't on the list). Halfway: `midAt(q,k,now)` = the ceil(n/2)-th work day of the period (from the quest's start in a first period); once passed it's fixed by `e.ck`, and if a change would move it onto a day already gone it becomes today. You need `midNeed` = a third of the target (`MID_FRAC`), else the days so far are lost and the streak resets (`st.lost` entry with `mid:true`). At the end: on the last day of a total's period, if `rollSum < weekTarget` (prorated to work days, so a pause or deletion mid-period prorates it rather than skipping the check), every ok/grace/frozen day from `weekFrom` (the quest's start) becomes `lost` (no longer counted in `st.total`), freezes earned on them are taken back, and the streak resets (only if something was lost or a streak was running). Which totals are checked: every total seen on a day's list in the period (`seen` in compute; `periodList(k)` for UI), unless it's user-optional (`activeDefs` stamps `uopt` on optional totals, since off days also carry `opt`). `perWorkDays` counts each day with that day's version, so changing a total's days mid-period keeps its target. `st.best` = most ok days between resets, so lost days never count. `st.lost` records it. During the period `#carryNote` (`renderCarryNote`, 37) shows the next checkpoint for each total (a third by the middle work day, then the full total by period end); notification 2600 fires at 09:00 on the earliest checkpoint a total is short for (halfway if a third isn't done yet, else period end; off days included); the pace (`rollNeed`) is advisory.
- **Modes: Challenge / Casual**: Settings › Quests & rules › Mode › "Challenge mode" switch (`#setStreak`, `setStreaks`) opens/closes a range in `cfg.noStreak = [{from, to?}]` (`to` exclusive; a Casual day = `noStreakOn(k)`, `modeOn(k)` names it, `rewardsOff()` = today is Casual). Asymmetric: Casual starts today; Challenge again from tomorrow (today during setup), so switching back can't rescue a failing day. Switching to Casual again while that's pending reopens the range; the switch shows tomorrow's state. Settings are never cleared by a switch — only their application is gated. **Casual**: XP, levels and rank are earned and shown (`totalXP`, `completionXP`, `weekCountOn` count every day; `#cleared` says "All done today!"); the day is marked `pause` (neutral, the streak waits); nothing is judged — no total checkpoints in a period that touches a Casual day, no streak-risk (2200)/checkpoint (2600) alerts, no reset card; badges (`badgeStats` skips Casual days, nothing awarded), grove and the period note are hidden with the streak stats (`body.nostreak`, `33-streak-pause.css`); easing changes and pauses apply at once (`guardEasing`/`pauseQuest`); Trends and the share card show days logged; totals show "10h / of 15h this week". **Challenge**: streak with grace and freezes, total checkpoints, badges, grove, easing changes from tomorrow (`cfg.lockDay`). SCHEMA 13 marks `noStreak`. **Ignore list** (paused days only): `cfg.ignore` = quest ids; swipe right on a row (or row menu "Ignore"/"Add back to the list", `setIgnore` in 45) toggles it, replacing swipe-right-to-done while paused. `ignoredOn(id,k)` → `activeDefs` marks the quest `opt` + `ign`, so it's out of the count, the schedule (`schQuests`), repeats and their reminders, Just 5, Pick, open to-dos; rows sit in a collapsed "Ignored (n)" group (`#ignSep`, `.ignq`, `pc-ignopen`). Time logged on it still counts. Kept while the last paused day runs out; cleared when a fresh pause starts (or on an immediate resume during setup). SCHEMA 15 marks `ignore`.
- **Per-quest streaks** (both modes, counters not judgments): `qStreak(id,k)` = consecutive scheduled days met up to k (today once met; days the quest wasn't on the list because it was unscheduled, paused, off, ignored or not yet added/seen (`addedOn` or `firstSeen`) are skipped, not broken); `qConsist(id,k)` = met/scheduled over the last 30 days. Daily time, check, target, scale and clock-time quests only (`qStreakable`). Rows show a flame chip `.qstk` from 2 days; Details has "In a row" and "Last 30 days".
- **Streak repair** (Challenge only): within `RESET_CARD_DAYS` of a reset, the reset card offers "Repair for `REPAIR_XP` (200) XP" (armed, two taps) when `xpNet()` ≥ 200: the day that reset the streak gets `e.rep = true` (compute treats it as cleared, strip mark `repaired`; `hasEntry` ignores `rep`), `cfg.xpSpent` grows, `S.refl[day] = {repaired:true}`. `xpNet()` = `totalXP()` − `xpSpent` drives the level everywhere; `totalXP` stays gross for badges.
- **Misses**: first miss = grace; second consecutive resets the streak unless a freeze is available (one earned every 14 clean days, `fzCap`). After a reset the streak simply restarts: no rebase, no gate. A dismissible **reset card** (`renderResetCard`, 21, `#resetCard` under the HUD, Challenge only, for `RESET_CARD_DAYS` 3) asks what broke it; Save/Skip writes `S.refl[day]` (`{text}` or `{skip:true}`).
- **Daily time quests**: minutes ≥ min. Plan is a stretch goal (gold day).
- **Week start**: `cfg.weekStart` 0 = Sunday, absent = Monday. `weekStart(k)` honours it, so every weekly rule follows; use `wkOrder()` for weekday chip order, `wkEndDay()`/`DAYF` for "until Saturday/Sunday", `wkSpan()` for "Mon–Sun". `nextMonday(k)` means "next week start". Changing it regroups past weeks.
- **Total quests (`q.roll`, minutes per period)**: `q.per` = absent (week), `"2w"` (two weeks counted from `weekStart(rollFrom(q))`) or `"month"` (calendar month). `perStart/perEnd/perWorkDays/perWord` in 26; `rollSum(id,k,q?)`, `rollNeed`, `weekTarget` (= this period's target), `emptyCover` and `schLen` all use the period. Late-in-week start only applies to weekly ones. SCHEMA 11 marks `per`/`weekStart`.
- **Weekly-total quests**: by default a fixed week. Pace by the quest's ticked **work days** (`rollNeed`): need by day k = min(straight-line share = target × workdays elapsed / workdays in period, done-before-today + what's left ÷ remaining work days incl. today). So a surplus still covers empty days, but a shortfall is spread over the rest of the period instead of landing on the next day. First week prorated from `startOn || addedOn || firstSeen`. On non-work days `activeDefs` marks it `opt` + `off`: it sits in a collapsed "Off today" group (`pc-offopen`), never counts as done, and is left out of the schedule, Just 5 and Pick; extra time logged there still counts toward the week.
- Carried days are retired (`carriedOK`/`emptyCover` return false/null) since totals no longer count day to day.
- **Start dates (`q.startOn`)**: hidden until then; listed under "Starting soon". Weekly totals created after Thursday noon default to next Monday.
- **Your day**: `cfg.day` = `{wake, bed}` (default 07:00–23:00); `cfg.dayOv` = `{date, wake, bed}` overrides one day. There is no separate "Day ends at": `dayEnd()` = `lockHour(bed, wake)` — midnight, or the usual bedtime when it's after midnight, rounded up to the hour (max 5 am). It drives `todayKey()` and the lock. SCHEMA 5 folded the old `cfg.dayEnd` into the bedtime. `dayWin(k)` → `{s, e}` in minutes from that day's midnight (`e` > 1440 past midnight). It is the only source of day bounds: midpoint, pace alert 2500, to-dos 2400 (bed − 30m), and the schedule. Clock-time (`wake`) quests are ordinary quests and never define the day. `winErr(w, b, today)` validates: ≥ 1h window, usual bedtime ≤ 5 am, wake after the lock, and a today-only bedtime no later than the usual lock.
- **Late start**: daily quests added after the midpoint of Your day (`dayMidMin`) are optional that day.
- **Schedule (today + 13 days ahead)**: `51-today-schedule.js`, a full-screen page (`#schPage`, `openSchedule`/`closeSchedule`; body gets `sch-open`, only `#schScroll` scrolls). Tap a free time → pick a quest in the footer (`schPick`); tap a block → footer controls (`schSel`); hold-drag moves (touch: 350 ms long-press); only the selected block gets a resize tab (`.sch-h`, 44×30 bottom-right, `touch-action:none`), so scrolling can never resize. Drags use timeline coordinates plus `schAutoScroll` (rAF loop while the pointer is within `SCH_EDGE` of the scroller’s top/bottom, or beyond it), so a held block follows the finger as the day scrolls; Auto-plan (`schAuto`) fills free gaps with what's left, 15-min breaks, ≥30m shots. `e.sched = [{id, q, f, t, j5}]` on the day entry (one entry per shot, so a quest can be split; SCHEMA 4 migrated the old `{questId: {f, t, j5}}` map), minutes on the `dayWin` scale. A new shot fills what's left of the daily share (or 30m once full) and stops short of the next block; Split halves a block. Read via `schAll`/`schOfQ`, write via `schSave`. Time quests only. Default length `schLen(q)` = min, or roll ÷ work days (ceil to 5). `j5` = 5-min start: fixed length, notification starts Just 5; otherwise a range (resizable, 15-min steps) whose notification starts the normal timer. No overlaps; quest shots never go before now; tapping a past time offers Block busy time…, and the busy editor has no "now" floor. `hasEntry` ignores `sched`, so a schedule never counts as logging. Notifications 3500+ carry `extra: {sched, j5}`; `notifAction` (52) calls `schTap`. `notifSync` reschedules when id, time, title, body or extra change. **Start/Resume** (`schLeftIn`): a quest block under way (now inside it; not j5) with no timer on its quest offers "Start · Xm left" (nothing timed inside it yet) or "Resume · Xm left" (`schResWord`; `schDoneIn`) in the block footer (`schRes`), in the default footer for the latest such block (`schResA`, no selection needed) and as "(Xm left)" on the quest row. Left = block length − minutes timed inside it, capped at the time until its end. The persistent notification is stricter (`schLeftIn(T,b,true)`): started, today's share/minimum (`timerMin`) not done, and not re-planned since you last worked in it (`schEdit` stamps `ed`; `schLastIn` < `ed` → none). `resumeSync` (called from `notifSync`) keeps one (id 905, `ongoing`, latest such block) until it's resumed, removed, the block ends (a timeout re-syncs at its end) or the day ends (`removeDeliveredNotifications`); off when schedule reminders are off; `resKey` starts as "?" so a leftover 905 is cleared on launch. `notifSync` also runs on return to the app. `schTap` ignores stale taps (no block for that quest today, or 905 no longer resumable). `schLeft`/Auto-plan count a running timer's minutes, and Auto-plan starts at the next 15-minute step after now. **Block progress** (`schDoneIn`, from `e.sess` + a running timer via `schSess`): a timed stretch credits each of the quest's blocks it overlaps with the overlap, and its part outside all of them to the block it overlaps most (late starts/overruns count, nothing double-counts; stretches touching no block credit none). Each block shows "· 40m of 1h" with a yellow bar (`.sch-pg`), and `.done` + ✔ only when its own length is done. The quest-level tick ("met today": `schDayDone` = today's share for totals, `metQ` otherwise) is on the tray chip (`.sch-q.done`), not on blocks; block reminders (3500+) also use `schDayDone`, so a total that's merely ahead of pace still reminds. **Re-plan** (`schShort`/`schReplan`): once a block has ended, short = length − credited − blocks already re-planned for it (`rf` = its id), capped at `schLeft` (what the quest still needs today after logged time and blocks ahead), shown ≥ 5m as "· 15m short" (`.short`); the block footer (`schRpl`) and the default footer (`schRplA`, first short block) place it from the next 15-min step in free time (≥ 15m pieces, tagged `rf`). Removing a re-planned piece brings the shortfall back. **Ended blocks** (`schEnded`: today and end ≤ now) are a record of the plan (Trends' plan kept reads them): drawn `.past` + `data-ro` (no drag/resize grip), and `schEdit`/`schRemove` refuse them (`SCH_ENDED`), so no move, resize, split, mode switch or remove; their footer shows Ended, what was done, Re-plan if short, Repeat/Edit repeat and Stop. A block under way can still be ended early or pushed back, but its passed part (up to `schCut()`, the current 15-min step) is kept too: in `schEdit`, moving it leaves `[f, cut]` behind as an ended block with the old id (the moved block gets a new id) and an edit can't pull its end before the cut; Remove trims it to the passed part (`Removed the rest…`; deleted outright if less than a step has passed); resize stops at the cut; Split never splits inside it; the range/5-min toggle is hidden once it has started (`schStarted`). Clear rest (Clear all on later days) only drops blocks that haven't started (and skips only those repeats). Stopping a repeat keeps today's occurrence as a one-off (same id, `src`) once it has started. **Planning ahead**: header ‹ › (`#schDP`/`#schDN`, `schGoDay`) set `schDay`; `schK()` = the viewed day (today, or up to `SCH_AHEAD` 13 days ahead; reset on open, falls back to today once passed) and every today-mode read/write uses it. A later day has no now floor, past shading, now line, Adjust today or Resume; Auto-plan starts at wake-up with the full share (`schLen(q,k)`). `schSave` writes a later day straight to `S.days[k]` without a `q` snapshot (deleted when empty), so it stays unlogged until that day; title "Today" / "Tomorrow" / "Fri, Nov 6".
- **Now button and hour scale**: `#schNowBtn` sits sticky at the bottom of `#schScroll` on today, shown only while the now line is off screen (`schNowVis` on scroll; "▲ Now"/"▼ Now"), and `schGoNow` scrolls the now line a third of the way down. `SCH_ROW` is set on open or day change (`schDraw(first)`): `SCH_ROW_DENSE` (16px per 15-min step) when the viewed day has under `SCH_DENSE_MIN` (120) min planned, else `SCH_ROW_FULL` (22); `#schTl` carries it as `--row` and `.dense`, and blocks under 45 min (30 at full scale) get `.sm`. Tests read `--row` (`rowPx`) instead of hard-coding 22.
- **Busy times and repeats**: busy times are a weekday template `cfg.busy = [{id, lb, f, t, dows, from, until?}]` edited on the same page in busy mode (`openBusy(wd, at, back)`; `schMd`, `schWd`; Settings › Your day › Busy times, the schedule’s Busy times button, or Block busy time… after tapping a time). A block applies from its `from` (the day it was added) on its weekdays, until `until` if set (expired ones are pruned on save and not counted in Settings); day toggles and moves are refused if they clash on any of its days. On Today they merge in read-only (`{id:"z-"+id, busy}`, `.ro`, no drag/resize); new shots and Auto-plan avoid them, shots already placed on top stay (`.clash`, drawn offset right) and still remind. SCHEMA 10 moved old busy shots/repeats into `cfg.busy`. Quest repeats: `cfg.rep = [{id, q, f, t, j5?, dows, from, until}]` repeats a block weekly; `schAll(k)` merges matching repeats as `{id:"r-"+rep, rep}` unless `e.schSkip` lists them. Edits to an occurrence go through `schEdit`, which detaches it into a one-off (`src` = its repeat) + skip; `schDet` then offers Every week (`schRepEvery`), and Repeat on a detached copy edits its series. Repeats and Every week are refused if they'd clash on a later day (`repClash`: other blocks, repeats, busy times). `schLeft` = daily share − minutes logged − blocks still ahead (Auto-plan uses it). Skip today = add to `schSkip`; Stop = drop the repeat; unticking today's weekday keeps today's block as a one-off. Blocks of quests not on today (`schList`) don't block placement or Auto-plan. Repeat/busy day labels follow `wkOrder()`. A quest repeat only lands on days the quest runs (`schRepDays`). SCHEMA 8 marks this shape; `hasEntry` ignores `schSkip`. Footer actions sit in `.sch-acts` rows (48px): a full-width primary row `.sch-pri` (Every week / Start·Resume / Re-plan) above the secondary row (Repeat, Split, Remove/Skip, Stop, ✕).
- **Pause** (`pauseQuest`, row menu "Pause until <last day of week>"): `pausedFrom` = tomorrow (today during setup or Casual), `pausedUntil` = `nextMonday(T)` (next week start), so a pause never crosses into the next week. On the last day of the week outside setup there is nothing left to pause, so the item is hidden.
- **Easing changes** (lower target, delete, pause, optional, remove days, later start, daily→total, raised limit) take effect tomorrow via `cfg.lockDay` (`guardEasing`, 25) in Challenge; at once in setup week and Casual. Strict mode, the weekly easing budget, per-quest change locks and their queued changes, commitment checks and the early-stop/broken-block penalty were removed (SCHEMA 16 drops `strict`, `easeLog`, `capSet`, quest `lock`/`lockFrom`/`pending`, day `brk`; files 34 and 36 are gone).
- **Daily quest limit** (`cfg.cap`, ≤10): counts required quests per weekday (`dayLoad`). No limit on total quests.
- **To-dos**: done ones deleted the next day; open ones get a keep/delete review the next time the app opens on a new day (or from notification 2400, 30 min before bed). There is no End day: days lock on their own (`lockHour`), past days are read-only, and `ended`/`endedAt` were dropped in SCHEMA 6.
- **Daily limit (`q.lim`, minutes/day, time quests only, daily or total)**: `limOf(q)`. Past it nothing is tracked that day: +/- and tap-to-type clamp, `logTimer` clamps, `schLeft` caps the day's share. `timerCap()` (13, run every tick and from notification 1004) stops a running timer at the exact moment the limit is reached (`stopTimer(end)`) and logs up to it, with `sfx("stop")` (descending) and a "Time's up" toast; starting a timer at the limit is refused. Notification 1004 "Time's up" is scheduled at that moment on its own channel `pc_stop` (sound `pc_stop.wav`, copied by `add-native.cjs`), and the live timer notification counts down to it, handing off to a "Time's up" state. Editors: "Daily limit, minutes (optional)"; must be ≥ the daily minimum (≥ 5 for totals). Row shows "· up to 1 hour/day".
- **Just 5**: first unfinished time quest in list order; all done → Bonus 5 picker. Timers and sprints start at once (no commitment prompt); the only early-stop prompt is Just 5's "Almost there".
- **Timer running** → forces Minimal view (`focusView`), shows one enlarged card, blocks leaving until stopped. Its first goal is `timerMin(q)`: a daily quest's minimum, or a total's daily share (`schLen`) — a total's own `min` is a leftover default and is never used ("Today's share done"; no plan goal for totals). A timer still running when its day locks keeps counting for its start day for `ROLL_GRACE` (60) min, and stopping it then logs the whole session to `t.day`. Past the grace it's split by `rollTimer` (render, stopTimer): minutes up to the lock go to `t.day` via `logTimer`, the timer restarts from the start of today (so a timer forgotten for days doesn't pile the gap onto today; no early-stop penalty). `logTimer` logs nothing (no session or topic time) if the quest isn't on that day. Sprints aren't split.
- **Topics are the unit; subjects classify them.** `q.topics` = topic ids the quest feeds; `q.subjs`/`q.subj` (first) are kept in step for subject minutes and finish lines (a topic-less subject can be linked whole). The running card lists the pool as chips (`.rb-tp`); `switchTopic` banks `now − tAt` into `S.timer.tacc`; `stopTimer` logs `topicSplit` (largest remainder, sums to the logged minutes) via `addTopicTime` → `e.tt`. - **Row subject box**: a quest that feeds subjects shows a small `.sjchip` "…" button under its title (red dot = a topic due for review; aria-label lists what it feeds). Tapping it pops a `popMenu` (`openSubjPick(q, btn)`, 35) of each topic in `qTopicPool` as "Subject › Topic · p/5" (topic-less subjects as "Subject · No topics yet"); each item jumps to the subject. Due when `pc-rerate` (the day it was last saved or skipped) is before this week's start and ≥ 2 days ago (so moving the week start doesn't ask twice); lists the top 3 topics by last week's `e.tt` with ≥ `RERATE_MIN` (60) min each; Save writes `setRating` (p + today's `hist`) only for ratings changed; Skip this week just stamps `pc-rerate`. Picks live in `rrPick` until saved.
- **Pick › topic review** runs on a quest feeding the topic, else one linked to its subject, else the Just 5 quest (the topic still gets the time).

## Design system (keep new UI consistent with this)
- Pixel look: Press Start 2P (`--px`) for headings/labels, VT323 (`--vt`) for body text. Panels `#C6C6C6` with bevel borders (light top-left, dark bottom-right); sunken areas reverse the bevel. Buttons are `.stone`; primary `.save` (green), destructive `.del` (red). On/off is always the `.sw` switch, never an "X on/off" button.
- Full-screen pages (Schedule `#schPage`, How it works `#helpPage`): dark header bar with a yellow Press Start title and a green Done, one scroll area (`overscroll-behavior: contain`), body class (`sch-open`/`hp-open`) to stop the page behind scrolling. Android back closes them.
- Settings (`10-settings-panel.js`): home list of categories (`SET_CATS`, each with a live summary) → a page per category built from `sgroup(title, rows, helpTopic)` and `srow(title, hint, control)`. Hints are one line; anything longer goes in How it works (`HELP` in `24-help-onboarding.js`, opened with `openHelp(topicId)`). Wiring uses `bind(id, …)` because only one category is in the DOM at a time.
- **Gestures**: swipe left on a list row = that row's menu (`popMenu`); hold = pick up and move (schedule blocks, drag grips, and on the phone the quest rows themselves: `sortable(..., holdSkip)` starts a drag after `HOLD_MS` 350 of a still touch anywhere on the row that isn't a control; the grip is hidden on phones). Delete is never a bare gesture: it sits in the menu as an armed item (`[label, fn, {arm:"Delete …?"}]` — first tap relabels, second runs). `swipeMenu(el, itemsFn, skipSel)` (45) wires it; used on Rulebook section headers (Edit / Delete), Subjects headers (Rename / Fold / Delete, `renameSubj`) and topic rows (Edit / Delete). Swipe right stays the quest list's done/ignore; the open to-do review (`reviewTodos`) answers both ways via `swipeLR` (right = keep, left = delete, `.dropq` strikes the row). Rulebook sections reorder by hold on phones too (`sortable(..., ".rules-body,…")`, grip hidden). Tests use `swipe(page, locator, dir)` from helpers.
- **Phone rows** (`35-compact-rows.css`, `mobileList` in 47): ~52px, no grip, the `...` subjects box inline after the label, and a `.qplay` button on every collapsed time row (one tap = `toggleTimer`; hidden while running, done, off or ignored). The `.qsum` box of a total shows today's figure from `rollNeed` as value-over-caption HTML (`qSummary`): "1h 29m / to go today", "✔ / on pace", "+40m / ahead of pace"; off days and tracking-only show "10h / of 15h this week". The quick to-do box (`#tdGhost`) is the first thing in the list on phones (CSS `order:-1` in `36-today-trims.css`; DOM position unchanged). The period note `#carryNote` sits above the list: one line, neutral; `.warm` when behind pace, `.hot` only on a checkpoint day that's behind; tapping it opens `openCarryInfo`. Saving is silent (no "Saved on this device"; `setSync` is for errors and actions); the privacy line lives in Settings › Your data › Backup, the page footer is empty. Toasts raised in the first `TOAST_HOLD` 3 s after launch wait for the first tap/key (`showToast`, 03), so retroactive badges never cover the header on open.
- **Today header (phone)**: `#lockIn` says "Locks in …" only in the last `LOCK_SOON` (120) min before the lock ("Locked" on a past day); the pencil and Minimal live in the ⋮ tools menu (`toggleFocusView`), the Minimal button itself shows only while Minimal view is on, as the way out.
- **Quest forms fold**: name, goal and days are primary; starts, daily limit, change rules, feeds topics (new quest: `NQ._more`, `#nqMoreOpt`) and project total, limit, note, starts, topics, finish line, change rules (Edit quests: `mqMore[id]`, `[data-more]`) sit under a "More options" button whose `<small>` carries `moreSum(q)` — what's set beyond the defaults. Tests open the fold before touching those fields.
- Details for a total: one pace sentence after "done of target" ("1h 12m more today keeps you on pace" / "on pace" / "ahead by 40m").
- Today-only wake/bed lives on the Schedule page ("Adjust today"), not in Settings.

## Badges and Trends
- Badges: `D.ach` (20, in `D.groups`) in `src/assets/achievements.json` with pixel icons (`D.icons`, 16×16 rows). `03-achievements.js`: `badgeStats(st)` scans history once, `BADGE_RULE[id](o)` → `[have, need, unit]`, `renderBadges(st)` (called from `render`) records newly met badges in `cfg.badges = {id: date}` (they stay earned; streak badges (`STREAKY`) only from settled days, `compute(settledAsOf())` = before any running total's period, else "Earned once this period's totals are in"), toasts once (several at once share one toast), and drives the desktop "Next badge" card (`nextBadge`). Certificates are drawn on demand by `certPDF`. Custom achievements were removed (SCHEMA 9 drops `cfg.customAch`). Toast kicker is "Badge earned!" (`showToast({kicker})` for other uses).
- Trends (`31-trends.js`, add-on page): this week (focus, days cleared, topic time, plan kept, reminders answered, deep sessions), top topics by time over 4 weeks with levels and 30-day level gains, focus by hour of day (from `e.sess`), 14-day focus, days cleared per week, records.
- Proficiency is only ever self-rated (`setRating`); time and quests never change it. `PROF_DO` anchors each level to a can-do test, shown under the pips and in the weekly check-in. `topicFlat(t)` flags effort without progress (≥ `STALL_MIN` 300 min in `STALL_DAYS` 28 days and no rating rise since the window began) on Subjects rows, the check-in and Trends.
- Subjects page boxes fold from their header (`.sjsec.fold`, ids kept in `pc-sjfold`).

## Splash
- `#splash` is in `index.html` (visible before JS runs, so cold start never flashes the app); `53-splash.js` animates it: the grove sapling (`drawPlant`) grows over a filling bar, with a status line (focusing / streak + today), ~1.25 s, tap skips, reduced motion = static 0.7 s. Shows on launch and on return after `SPLASH_AWAY` (30 min) hidden. A CSS fallback hides it at 4 s if JS fails. No Minecraft imagery: we're moving away from it.
- Native launch screen is a plain `#212121` (no icon) so it hands off seamlessly; `add-native.cjs` writes `pc_splash_blank.xml` and patches `AppTheme.NoActionBarLaunch` in `styles.xml`.
- Tests: `openApp` sets `pc-splash=off` unless `extra` sets it (`splash.spec.mjs` turns it on).

## Sound and haptics
- `haptic(k, quiet)` also plays a short 8-bit click (`tapSound`) for light/medium/heavy taps unless `quiet`; `sfx()` passes `quiet` so game sounds don't double up. Muted by Settings › Tap sounds (`cfg.tapSound`) or the master Sound toggle (`sfxOn`, `pc-sfx`). Vibration (`cfg.haptics`) is separate.

## Notifications (native only; inert on web)
- `nfPlan()` builds the schedule; `notifSync()` diff-reschedules via `@capacitor/local-notifications` on channel `pc_alerts2` (sound `pc_chime.wav`).
- IDs: 901 live timer, 905 resume block (ongoing), 1001–1003 timer goals, 1004 time's up (channel `pc_stop`), 1101–1103 sprint, 2000+ check-in, 2200 streak risk, 2300 carry cover, 2400 open to-dos, 2500 day midpoint pace, 2600 period-total checkpoint, 3000+ deadlines, 3500+ today's schedule starts, 3700 + day×20 + n quest blocks (planned or repeats) on the next 13 days, 4001 review topics, 4998/4999 tests.
- **Answered the call**: every scheduled notification carries `extra.at` (fire time). Tapping a reminder (check-in, streak risk, carry, midday/weekly pace, schedule start) within `CALL_MIN` (2) min sets `S.call`; the next timer/Just 5/sprint start (`callCheck`) adds `e.calls`, worth `CALL_XP` (10) each in `dayXP`, capped at `CALL_CAP` (5)/day. `hasEntry` ignores `calls`. Constants live in `00-core.js` because `dayXP` runs during startup.
- **Tapping a notification** runs `notifAction(id, extra)` (`52-notification-actions.js`): each id opens its own prompt (`nfCall`) or screen — timer prompts with Stop & log / Keep going, sprint panel, check-in / streak-risk lists with Just 5 on the furthest-behind quest, to-do review, midday/weekly progress bars, deadline (extra `{dl}`) → Plan today, review topics, schedule starts → `schTap`. Live timer taps: native puts `pcTap` on the launch intent, `MainActivity` (written by `add-native.cjs`) passes it to `FocusNotifyPlugin.capture`, JS reads it with `FocusNotify.takeTap()` on open and on return to the front.
- Live timer: custom plugin `FocusNotify` (channel `pc_focus_live2`, id 901) with a Chronometer RemoteViews layout. Countdowns hand off at zero via an exact AlarmManager alarm → `FocusNotifyReceiver`. Timestamps must be passed as integers (`Math.round`) and read with `optLong`. Growing sapling: JS passes `grow = {from, dur, art}` (`focusArt()` renders 7 `drawPlant` stages as 24×36 PNGs; goal = plan/min, weekly share for roll quests, 5 min for Just 5, block length for sprints, none while paused). Native picks the stage from `(now − from) / dur`, upscales nearest-neighbour, fills `pc_prog` (big layout only — never touch an id a layout lacks), and re-posts itself at the next stage via a second alarm (request 9012, skipped when it would collide with the countdown handoff). Expanded layout `notif_focus.xml` is a fixed 196dp (Android caps expanded custom views at ~252dp; the collapsed height is set by the system and can’t grow): 80×120dp sapling, 44sp timer. Bitmaps are upscaled nearest-neighbour to `ART_HEIGHT_PX` 324 / `BG_HEIGHT_PX` 432 / `BG_SMALL_PX` 128. Background: JS passes `bg = {big, small, dark}` (`focusBg()`: 96×54 / 120×16 pixel day or night sky over grass, cached per day/night); native upscales it into `pc_bg` (a FrameLayout behind the content in both layouts) and sets light or dark text colours. Every posted state, including `next` handoffs, carries `bg`. Stopping always goes through `focusOff()` (hides 901 and cancels the fallback 900) via `focusSync(true)`; the app also clears a leftover live notification on open when nothing is running.
- Android caveats: exact alarms need `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` (remove `USE_EXACT_ALARM` before Play Store); channel importance/sound are immutable once created — use a new channel id to change them.

## Testing patterns
- `openApp(page, { now, cfg, days, extra, hash })` installs a fake clock and seeds storage; then drive the real UI.
- Mock native plugins by defining `window.Capacitor = { isNativePlatform: () => true, Plugins: {...} }` in `addInitScript` (see `native.spec.mjs`, `pace.spec.mjs`).
- Prefer `expect.poll` / `toBeHidden` over fixed waits; parallel runs expose races.
- Phone layout tests use `test.use({ viewport: { width: 360|390 }, isMobile: true, hasTouch: true })`.
